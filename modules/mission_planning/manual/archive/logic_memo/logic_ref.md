# Mission Planning Logic Reference

## 문서 목적
이 문서는 `modules/mission_planning`에서 현재 실제로 동작하는 임무계획/재계획 로직을
코드가 아니라 운용 시나리오 관점으로 정리한 참조 문서다.

정리 범위는 아래와 같다.

- 초기 임무계획
- 일반 재계획
- 선행임무 재계획
- 표적 발견 기반 공격 재계획
- 강제명령/가용성 변화로 인한 재계획 연동
- 임무계획 모드별 차이
- 기존 임무를 보존하면서 재계획하는 방식
- 계획 실패/소요시간 표시 방식

---

## 1. 이 모듈이 만드는 출력
임무계획 모듈은 최종적으로 아래 산출물을 만든다.

- `0301`: 최종 MissionPlan
- `0302`: 기체별 개별임무 패키지(IMP)
- `0303`: UAV FlightPath
- `0304`: LAH FlightPath
- `0305`: 임무계획 진행/완료 상태 전송
- `0001`: 계획 실패 시 핵심 원인 공지

즉, 이 모듈은 단순히 경로만 만드는 것이 아니라,
"어떤 기체가 어떤 임무를 어떤 순서로 수행할지"까지 포함한 최종 실행 패키지를 만든다.

---

## 2. 주요 입력

### 2.1 기본 계획 입력
- `0201 InputMissionPlan`
  - 입력 임무 목록
  - 임무 유형(Line / Area / Formation 등)
  - 사용 가능 기체 목록
  - 각 협업기저임무의 `isDone` 상태

- `0203 MissionReferenceInfo`
  - UAV take-over 지점
  - UAV hand-over 지점
  - 비행 구역

### 2.2 현재 수행 상태 입력
- 기체 상태 정보
  - 현재 좌표
  - 속도 / heading
  - 현재 waypoint
  - 비가용 여부

- 임무 진행 정보
  - 현재 수행 중인 개별임무
  - 진행 중인 waypoint
  - waypoint 완료 여부
  - sweep 진행도

### 2.3 표적 / 공격 관련 입력
- `0402` 표적 보고
- `targetInfo.json`
  - 표적 좌표
  - watcher UAV
  - 파괴 여부
  - 이미 재계획에 사용되었는지 여부

### 2.4 선행임무 입력
- `0202 PriorMissionInfo`
  - 좌표지향 선행임무
  - 표적추적 선행임무
  - 어떤 협업기저임무 중간에 끼워넣을지

### 2.5 계획 보조 입력
- `resource/db/fov_db.csv`
  - FOV / SEP / 속도 선택용 DB
- DEM / GeoTIFF
  - 지형고도 참조
- `MissionPlanner/uav_params.json`
  - 임무계획 공통 설정
  - `main_MP`와 실제 `mission_planning_gui.py`가 같은 설정 파일을 공유함

## 3. 공통 계획 흐름
모든 계획/재계획은 큰 틀에서 아래 순서를 따른다.

1. 입력 검증
2. 대상 임무 추출
3. 임무를 UAV/LAH 기준 조각으로 분할
4. 각 조각의 expected path / expected velocity 계산
5. 스케줄링 및 기체 할당
6. `0302` 생성
7. `0303`, `0304` 생성
8. `0301` 저장 및 `0305` 완료 전송

중간에 입력이 부족하거나 산출물이 일부라도 비면,
조용히 실패하지 않고 `0001` 공지로 핵심 원인을 한글 문장으로 알린다.

예시:
- `0201 입력 임무 파일을 찾을 수 없습니다.`
- `0203 비행참조정보 데이터가 부족하거나 형식이 올바르지 않습니다.`
- `일부 비행경로 데이터가 누락되어 임무계획을 완료할 수 없습니다.`

---

## 4. 초기 임무계획

### 4.1 언제 실행되나
- 새로운 `0201`, `0203`가 들어왔을 때
- 사용자가 초기 임무계획 모드로 전환했을 때

### 4.2 무엇을 하냐
- 아직 끝나지 않은 협업기저임무만 대상으로 삼음
- Line / Area / Formation 입력을 보고 UAV, LAH 임무로 푼다
- UAV 임무는 `0302`의 개별임무와 `0303`의 비행경로로, LAH는 `0304`로 변환한다

### 4.3 결과
- 기본 임무계획 세트가 새로 생성됨
- MissionPlan에 기체별 IMP가 매핑됨
- 이후 monitoring / sim이 그대로 받아서 수행 가능 상태가 됨

---

## 5. 일반 재계획

### 5.1 언제 실행되나
- 협업기저임무가 추가되거나 순서가 바뀌었을 때
- 기존 `0201` 내용이 바뀌었을 때
- 강제명령/상황변화로 옵션 2~3개를 다시 만들어야 할 때

### 5.2 대상 임무 선정 원칙
재계획이라고 해서 항상 `0201` 전체를 처음부터 다시 푸는 것은 아니다.

- `isDone=True`인 협업기저임무는 기본적으로 제외
- 재계획 대상이 특정 임무로 좁혀져 있으면 그 임무만 다시 포함
- 현재 진행 중인 임무는 현 시점 기준으로 잘라서 resume 구조로 재구성

즉 재계획의 핵심은
"남아 있는 임무만 다시 조합해서 새 MissionPlan을 만드는 것"이다.

### 5.3 옵션 생성
일반 재계획에서는 보통 3개 옵션을 만든다.
현재 매핑은 아래와 같다.

- `정찰/시간 균형` → `Bearing_Par_Sweep Mode`
- `정찰 특화` → `Nadir Mode`
- `최소 시간` → `Bearing_Ver_Sweep Mode`

즉 같은 입력 Area라도 옵션별로 다른 계획 모드를 적용한다.

### 5.4 병렬화
일반 재계획의 2~3개 옵션 생성은 현재 병렬로 계산한다.
다만 최종 저장과 옵션 번호 매핑은 순서를 보존하도록 직렬로 정리한다.
즉,
- 계산은 빠르게
- option ID / missionPlan ID 연결은 안정적으로
유지하는 구조다.

## 6. 선행임무 재계획
선행임무는 기존 협업기저임무 중간에 새로운 개별임무를 끼워넣는 방식이다.

### 6.1 유형
현재 선행임무는 두 가지를 지원한다.

- 좌표지향 선행임무
- 표적추적 선행임무

### 6.2 어떤 UAV가 맡나
- 표적추적형이면 `targetInfo`에 watcher UAV가 있으면 그 UAV 우선
- watcher가 없으면 목표에 가장 가까운 UAV 선택
- 좌표지향형이면 좌표에 가장 가까운 UAV 선택

즉 선행임무용 UAV를 새로 최적화하는 구조가 아니라,
상황에 가장 자연스러운 UAV 1대를 뽑는다.

### 6.3 선행임무를 맡은 UAV는 어떻게 바뀌나
이 UAV는 기존 임무를 덮어쓰지 않는다.
기존 임무를 세 조각으로 재구성한다.

- `기존 임무의 이미 수행한 부분`
- `선행임무`
- `원래 하던 임무의 나머지(resume)`

구조로 쓰면 아래와 같다.

- 원래: `A`
- 재계획 후: `A_done -> 선행임무 -> A_resume`

세부 원칙은 아래와 같다.

- 기존 path 앞부분은 `isDone=true`로 보존
- 선행임무용 새 개별임무 / 새 path 생성
- 원래 하던 임무는 resume 개별임무 / resume path로 재생성
- 앞뒤 다른 개별임무들은 그대로 유지

### 6.4 선행임무 path 성격
현재 선행임무 path는 "긴 진입-이탈 경로"보다
"목표점 중심의 loiter 임무"에 가깝다.

- 좌표지향 선행임무
  - 목표 좌표를 보도록 촬영 설정
  - loiter 중심
  - 기본 loiter 시간: 50초

- 표적추적 선행임무
  - auto-tracking 사용
  - 목표 표적 ID를 개별임무와 WP에 같이 반영
  - 기본 loiter 시간: 300초

### 6.5 다른 UAV들은 어떻게 처리되나
선행임무를 맡지 않은 UAV들은 선행임무를 새로 받지 않는다.
대신 기존 임무를 현재 시점 기준으로 잘라서 이어간다.

구조는 아래와 같다.

- 원래: `B`
- 재계획 후: `B_done -> B_resume`

즉 다른 UAV들은
- 이미 지난 WP / sweep는 done으로 남기고
- 아직 안 한 부분만 resume으로 새 path를 만든다.

### 6.6 sweep 진행도 반영
resume path를 만들 때는 단순히 current waypoint만 보는 것이 아니라,
monitoring에서 쌓인 sweep 진행도도 반영한다.
즉 이미 훑은 sweep point는 resume에서 잘라낸다.

## 7. 표적 발견 기반 공격 재계획
공격 재계획은 선행임무보다 구조가 더 복잡하다.
핵심은 아래 세 갈래다.

- 표적을 추적하는 UAV
- 공격하러 가는 LAH / 유인기
- 추적하지 않는 나머지 UAV

### 7.1 언제 공격 재계획 대상이 되나
표적이 들어왔다고 항상 공격 재계획을 하지는 않는다.
아래 조건을 본다.

- `targetID > 0`
- 좌표가 유효함
- `isDestroyed == false`
- `isUsed == 0`
- `isIgnored == 0`

즉
- 이미 파괴된 표적
- 이미 재계획에 사용된 표적
- 좌표가 비정상인 표적
은 공격 재계획 대상이 아니다.

### 7.2 추적 UAV는 어떻게 바뀌나
표적을 본 UAV는 기존 임무를 유지한 채,
중간에 추적 임무를 끼워 넣는다.

구조는 아래와 같다.

- 원래: `A`
- 재계획 후: `A_done -> tracking -> A_resume`

세부 원칙:
- 기존 임무 앞부분은 `done`으로 남김
- 추적용 개별임무를 새로 생성
- 나머지 원래 임무는 resume 개별임무로 재생성
- 기존 path를 통째로 지우지 않고 시각화용 done path로 남김

### 7.3 추적하지 않는 UAV는 어떻게 바뀌나
다른 UAV들도 기존 임무를 처음부터 다시 하지 않도록 조정한다.
즉,
- 이미 지난 waypoint 제거
- 이미 한 sweep 제거
- 남은 구간만 resume path로 재생성

즉 공격 재계획 때문에 다른 UAV가 이미 끝난 구간을 다시 훑지 않게 한다.

### 7.4 공격 기체는 어떻게 생성되나
공격 쪽은 LAH/유인기를 별도 선정해서
- 진입
- 공격 waypoint
- 이탈
을 생성한다.
불필요한 hovering/loiter/attack 블록은 줄이고,
필요한 임무 속성만 남기도록 정리되어 있다.

### 7.5 다수 표적
한 타임스텝에 표적이 여러 개 들어오면,
현재는 조건을 만족하는 표적들에 대해 병렬 공격 재계획이 가능하다.
다만 이미 `isUsed=1`이 된 표적은 다시 사용하지 않는다.

## 8. 강제명령 / 상태기반 재계획
모니터링과 연결된 재계획 트리거는 아래와 같다.

- 협업기저임무 추가
- 협업기저임무 순서 변경
- 협업기저임무 재수행
- 좌표지향 선행임무
- 표적추적 선행임무
- 표적 발견 후 공격 특화 / 공격 배제
- 강제명령(임무 대기)
- 강제명령(임무 복귀)
- UAV 연료 부족
- UAV 비가용 / health 이상
- 입력 임무 갱신 재계획

이 중 일부는 monitoring이 먼저 상황을 감지하고,
mission planning은 그 결과로 새로운 plan option을 만든다.

## 9. Line / Area 계획 방식

### 9.1 Line 임무
Line 임무는 구간을 나눠 UAV가 맡도록 분할하고,
route와 촬영 sweep를 분리해서 다룬다.

- waypoint coordinate: 기체 비행 route
- `filmingProperty.lineSearch.coordinateList`: 실제 촬영 sweep

현재 line의 entry는 아래 원칙을 가진다.

- 기본적으로 임무 첫 구간 방향 기준으로 뒤로 빼서 생성
- takeOver 지점과 첫 임무점이 매우 가까우면 entry 생략 가능
- Par 모드에서는 전체 WP를 fly-over로 강제할 수 있음

### 9.2 Area 임무
Area 임무는 먼저 영역을 UAV 조각으로 나누고,
그 조각별로 route와 sweep를 만든다.

기본 개념은 아래와 같다.

- 분할 축
- move bearing
- sweep bearing
- DB 기반 SEP/FOV
- route와 sweep 분리

즉 단순히 면적만 균등분할하지 않고,
이전 임무/다음 임무 방향을 함께 고려해서 조각을 만든다.

### 9.3 Review Area
Area 조각이 너무 길거나 커지면,
추가 세분화를 해서 scheduling과 실제 경로 생성 안정성을 높인다.

다만 이 단계는 모든 모드 공통은 아니다.

- 일반 sweep 모드: 사용 가능
- `Nadir Mode`: 사용하지 않음

## 10. 현재 지원하는 임무계획 모드

### 10.1 Bearing_Par_Sweep Mode
현재 기본 sweep 모드다.

개념:
- bearing과 평행한 방향의 sweep
- area route는 그 sweep에 대응하는 offset route
- line/area 모두 같은 일반 sweep 철학을 따름

특징:
- 현재 가장 많이 다듬어진 기준 모드
- 일반 재계획의 `정찰/시간 균형` 옵션에 사용
- `전체 WP Fly-over`가 기본으로 켜짐

### 10.2 Bearing_Ver_Sweep Mode
Par 모드와 같은 입력 구조를 쓰지만,
area에서 사용하는 sweep 방향을 반대로 가져가는 모드다.

개념:
- bearing 기준 수직 sweep
- 같은 area라도 Par와 다른 촬영 패턴 생성

특징:
- 일반 재계획의 `최소 시간` 옵션에 사용
- 빠르게 훑는 성격의 대안 계획으로 취급

### 10.3 Nadir Mode
직하방 촬영 전용 모드다.

개념:
- area를 bearing line 기준으로 직접 분할
- review area를 사용하지 않음
- area는 `patternType=3`으로 내려감
- 최종 path 자체가 nadir 촬영 path가 됨

즉 일반 sweep 모드처럼
- route는 따로
- sweep는 따로
가 아니라,
Nadir 모드에서는 path와 촬영 경로가 거의 동일하다.

FOV 규칙:
- UAV 고도를 기준으로 DB를 조회
- `SEP <= 고도`를 만족하는 DB 행 중
- 가장 큰 FOV를 선택
- 그 FOV로 nadir 경로 간격을 결정

일반 재계획의 `정찰 특화` 옵션은 이 모드를 사용한다.

### 10.4 Custom Mode
수동 조정 모드다.

원칙:
- preset 대신 사용자가 직접 파라미터를 조정
- DB 대신 수동 FOV/SEP를 직접 쓰도록 구성 가능
- `main_MP`와 실제 임무계획 GUI가 같은 설정 파일을 공유

즉 테스트에서 바꾼 설정을 실모듈도 같은 방식으로 바로 쓰게 되어 있다.

## 11. 스케줄링 / 속도 / DB 연동
현재 계획은 단순 geometry만이 아니라,
속도와 촬영 조건도 함께 연동한다.

### 11.1 DB 기반 계획
일반 Line / Area에서는 DB에서
- SEP
- FOV
- 속도
를 선택해서 계획에 반영한다.

### 11.2 수동 계획
Custom 모드에서는 필요 시 DB를 끄고,
설정창의 수동값을 직접 사용한다.

### 11.3 스케줄링
스케줄링은 piece를 어떤 UAV가 어떤 순서로 수행할지 결정한다.
즉 분할만 하는 것이 아니라,
실제 기체별 수행 순서와 속도까지 결정하는 단계다.

## 12. 기존 임무를 보존하는 방식
재계획의 핵심은 기존 임무를 완전히 없애지 않는다는 점이다.

### 12.1 done / resume 구조
현재는 재계획 시 기존 path를 통째로 삭제하지 않고,
다음 두 개로 분리한다.

- `done path`
  - 이미 수행한 구간
  - `isDone=true`
- `resume path`
  - 앞으로 수행할 구간
  - `isDone=false`

이렇게 해야
- 시각화가 유지되고
- 실제 수행은 아직 안 한 구간만 이어서 할 수 있다.

### 12.2 현재 시점 반영
resume은 단순 복사본이 아니다.
아래를 반영해서 다시 만든다.

- current waypoint
- 현재 실제 위치
- 완료된 waypoint
- monitoring이 추정한 sweep 진행도

즉 "현재 시점 이후만 남긴 새 임무"라는 점이 중요하다.

## 13. GUI / 운용 측면

### 13.1 알고리즘 설정
임무계획 GUI에는 알고리즘 설정 탭이 있으며,
여기서 아래를 바꿀 수 있다.

- 계획 모드(Par / Ver / Nadir / Custom)
- FOV / SEP / 고도 / entry offset
- review area 사용 여부
- fly-over 옵션
- 유인기 계획 모드(현재는 UI/저장만 연결)

### 13.2 계획 시간 표시
GUI 상단에는 최근 임무계획 소요시간을 보여주는 배지가 있다.
이 값은 `0305` 진행/완료 상태를 기준으로 측정된다.

즉 선행임무, 공격, 일반 재계획 포함해서
"이번 계획이 실제로 몇 초 걸렸는지"를 운용자가 바로 볼 수 있다.

### 13.3 실패 공지
계획이 실패하면 내부 로그만 남기는 것이 아니라,
`0001` 공지를 통해 운용자에게 핵심 원인을 한글로 알려준다.

## 14. 현재 운영 기준 요약
현재 임무계획 모듈은 다음 철학으로 정리되어 있다.

- 입력 전체를 무조건 처음부터 다시 풀지 않는다.
- 이미 끝난 임무는 최대한 보존한다.
- 진행 중 임무는 현재 시점 기준으로 잘라서 resume한다.
- 상황에 따라 다른 재계획 모드를 선택할 수 있다.
- 일반 재계획 3안은 서로 다른 계획 모드를 사용한다.
- 선행임무와 공격 재계획은 기존 임무 중간에 새 임무를 끼워 넣는다.
- 실패하면 조용히 멈추지 않고 원인을 공지한다.
- `main_MP`와 실제 모듈은 같은 설정 체계를 공유한다.

즉 현재 구조는
"한 번 만든 계획을 계속 버리는 방식"이 아니라,
"기존 계획을 최대한 살리면서 필요한 부분만 다시 짜는 방식"으로 이해하면 된다.
