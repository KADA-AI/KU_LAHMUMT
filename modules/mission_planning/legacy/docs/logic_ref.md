# Mission Planning Logic Reference

## 문서 목적
이 문서는 `modules/mission_planning`에서 현재 실제로 동작하는 임무계획 로직을
코드가 아니라 운용 시나리오 중심으로 정리한 참고 문서다.

핵심은 아래 세 가지다.

1. 어떤 입력이 들어오면 어떤 종류의 임무계획이 시작되는지
2. 계획된 임무가 어떤 순서로 쪼개지고, 누구에게 배정되고, 어떤 비행경로로 바뀌는지
3. 재계획 상황에서 기존 임무를 어떻게 유지하고, 어떤 임무를 새로 끼워 넣는지

---

## 1. 임무계획 모듈이 하는 일
임무계획 모듈은 크게 네 가지 상황을 처리한다.

1. 초기 임무계획
2. 일반 재계획
3. 선행임무 재계획
4. 표적 발견 기반 공격 재계획

출력은 다음과 같다.

- `0301`: 최종 임무계획 묶음
- `0302`: 기체별 개별임무 패키지
- `0303`: UAV 비행경로
- `0304`: LAH 비행경로

계획 실패 시에는 조용히 끝나지 않고 `0001` 공지로 핵심 원인을 한글로 알린다.

---

## 2. 주로 참조하는 입력

### 2.1 기본 입력
- `0201 InputMissionPlan`
  - 어떤 협업기저임무가 있는지
  - 각 임무가 선형 임무인지, 영역 임무인지, 편대비행인지
  - 어떤 기체를 사용할 수 있는지
  - 어떤 임무가 이미 끝났는지

- `0203 MissionReferenceInfo`
  - UAV 인수 지점
  - UAV 인계 지점
  - 비행 구역

### 2.2 현재 상황 입력
- 기체 상태 정보
  - 현재 좌표
  - 속도
  - heading
  - current waypoint
  - 비가용 여부

- 임무 진행 정보
  - 현재 어떤 협업기저임무를 수행 중인지
  - 어떤 개별임무를 수행 중인지
  - waypoint가 어디까지 완료되었는지
  - sweep가 어디까지 진행되었는지

### 2.3 표적/공격 관련 입력
- `0402` 표적 보고
- `DSS_Internal/targetInfo.json`
  - 표적 좌표
  - watcher UAV
  - 살아있는 표적인지
  - 이미 공격 재계획에 사용된 표적인지

### 2.4 선행임무 입력
- `0202 PriorMissionInfo`
  - 좌표지향
  - 표적지향
  - 어떤 입력임무에 끼워 넣을 것인지

### 2.5 계획 보조 입력
- `resource/db/fov_db.csv`
  - FOV / SEP / 속도 선택용 DB

- DEM / GeoTIFF
  - 지형 고도 참조
  - 공격 지점 및 임무 고도 생성 보조

- `MissionPlanner/uav_params.json`
  - 임무계획 설정의 단일 원본
  - `main_MP`와 실제 `mission_planning_gui.py`가 같은 설정 파일을 쓴다

## 3. 임무계획의 공통 흐름

### 3.1 입력 검증
계획을 시작하기 전에 먼저 아래를 확인한다.

- `0201`이 존재하는지
- `0203`이 존재하는지
- 임무 목록이 비어 있지 않은지
- 기체 목록이 비어 있지 않은지
- UAV / LAH 구성이 최소 조건을 만족하는지
- 각 임무가 선형/영역 형식상 최소 조건을 만족하는지

이 단계에서 실패하면 `0001` 공지로 원인을 알린다.

예:
- `0201 입력 임무 파일을 찾을 수 없습니다`
- `0203 비행참조정보 데이터가 부족합니다`
- `일부 비행경로 데이터가 누락되어 임무계획을 완료할 수 없습니다`

### 3.2 현재 시점 기준으로 “남은 임무”만 다시 구성
재계획일 때는 0201 전체를 처음부터 다시 쓰지 않는다.

- 이미 `isDone=True`인 협업기저임무는 제외
- 재계획 요청이 특정 입력임무만 대상으로 지정되면 그 임무만 다시 포함
- 현재 진행 중인 임무는 진행 상태를 반영해 trimming / resume 구조로 다시 구성

즉 재계획의 핵심은
“남은 임무만 다시 조합해서 새 임무계획을 만든다”는 것이다.

### 3.3 임무를 기하학적으로 쪼개기
임무를 바로 waypoint로 만들지 않고, 먼저 UAV가 담당할 조각으로 나눈다.

- 선형 임무는 구간 단위로 쪼갠다
- 영역 임무는 진입 방향과 다음 임무 방향을 고려해 쪼갠다
- 쪼갠 결과는 “누가 맡을 임무 조각인지”에 가까운 중간 결과다

### 3.4 예상 경로와 예상 속도 계산
각 조각에 대해

- 어디 방향으로 수행할지
- 어떤 sweep 방향을 가질지
- 대략 어떤 속도와 FOV/SEP를 쓸지

를 계산한다.

이 단계에서 DB 기반 계획 또는 수동값 기반 계획이 반영된다.

### 3.5 스케줄링/배정
쪼개진 임무 조각을 UAV들에 배정한다.

현재 관점에서 중요한 것은 아래 두 가지다.

- 어떤 UAV가 어떤 piece를 맡는지
- piece 수행 순서가 어떻게 되는지

이 결과가 나와야 이후 0302/0303/0304를 안정적으로 만든다.

### 3.6 최종 산출물 생성
마지막으로

- `0302` 개별임무
- `0303` UAV 비행경로
- `0304` LAH 비행경로
- `0301` 최종 미션플랜

을 만든다.

## 4. 선형 임무 시나리오

### 4.1 상황
예를 들어 선형 감시/통로정찰/경로정찰 임무가 들어온다.

### 4.2 계획 방식
1. 선형 경로를 UAV 수에 맞게 여러 구간으로 분할한다
2. 각 구간마다 어느 방향으로 들어갈지 정한다
3. DB 또는 수동 설정을 이용해 FOV/SEP/속도 기준을 정한다
4. 실제 비행 route와 촬영 sweep를 분리해 만든다

### 4.3 route와 sweep의 관계
선형 임무는 기본적으로

- 기체가 날아가는 route
- 카메라가 실제로 훑는 sweep

를 분리해서 가진다.

즉,
- waypoint 좌표는 비행체 route 쪽
- `lineSearch.coordinateList`는 촬영 sweep 쪽

으로 생각하면 된다.

### 4.4 첫 진입점
첫 waypoint 앞에는 필요 시 entry 성격의 보정 점을 붙인다.

현재는 모드/순서에 따라

- 인수지점 기준
- 이전 임무 마지막 점 기준
- 현재 첫 구간 방향 기준

으로 entry가 만들어진다.

---

## 5. 영역 임무 시나리오

### 5.1 상황
영역 수색, 영역 감시, 영역 경계 비행 같은 임무가 들어온다.

### 5.2 영역을 자를 때 보는 것
영역은 단순히 면적만 균등 분할하지 않는다.

먼저 아래를 본다.

- 이전 임무 마지막 방향
- 현재 영역 중심으로 들어오는 방향
- 다음 임무로 빠져나갈 방향

이렇게 만든 “주 bearing”을 기준으로
영역을 어느 방향으로 자를지 결정한다.

### 5.3 Review Area
영역 조각이 너무 크거나 너무 길면,
한 번 더 잘게 쪼개서 계획 안정성을 높인다.

이 과정은 모든 모드에 공통이 아니고,
모드에 따라 사용 여부가 다르다.

예:
- 일반 sweep 모드에서는 사용 가능
- `Nadir Mode`에서는 사용하지 않음

### 5.4 영역 route와 sweep
영역 임무도 선형 임무와 마찬가지로

- route
- filming sweep

를 분리해서 가진다.

다만 최종 route는 각 mode의 기준축에 맞춰 정리되고,
sweep는 그 route에 대응하는 실제 촬영 구간으로 들어간다.

## 6. 현재 지원하는 임무계획 모드

## 6.1 Bearing_Par_Sweep Mode
이 모드는 현재 기본 기준 모드다.

개념은 다음과 같다.

- 영역 분할과 경로 생성을 bearing 축 기준으로 정리
- sweep는 bearing과 평행하게 생성
- route는 sweep에 대응하는 offset 형태로 생성
- line / area 모두 공통 설정을 사용

이 모드는 지금까지 가장 많이 다듬어진 기준 모드다.

## 6.2 Bearing_Ver_Sweep Mode
이 모드는 `Bearing_Par_Sweep Mode`와 같은 입력 구조를 쓰지만,
영역 처리 방향이 다르다.

차이는 다음과 같다.

- 영역 분할 방향을 반대로 사용
- sweep 방향도 기존 모드와 직교하는 방향으로 생성
- 결과적으로 같은 area라도 다른 패턴의 수색 경로가 나온다

즉 같은 영역을 두고도

- 하나는 bearing 평행 sweep
- 하나는 bearing 수직 sweep

으로 다른 임무계획을 만들 수 있다.

## 6.3 Nadir Mode
이 모드는 직하방 촬영 전용 모드다.

핵심은 다음과 같다.

- 영역을 bearing 기준으로 직접 분할
- Review Area를 사용하지 않음
- area 임무는 `patternType=3`으로 내려감
- 최종 path가 곧 nadir 촬영 경로가 됨

즉 일반 모드처럼
“route는 따로, sweep는 따로”
가 아니라,

`Nadir Mode`에서는
“nadir path 자체가 실제 path”
가 된다.

또한 FOV는 고도 기준 DB 선택 규칙을 따른다.

예:
- UAV 고도가 650m라면
- `SEP <= 650`인 DB 항목 중
- 가장 큰 FOV를 선택

이렇게 고른 FOV로 nadir 경로 간격을 결정한다.

## 6.4 수동 FOV 모드
이 모드는 기본 임무 계획 프리셋 안에서 사용자가 FOV/SEP를 수동으로 조정하는 모드다.

현재 규칙은 다음과 같다.

- 기본 임무 계획은 DB 기반 값을 사용할 수 있음
- 수동 FOV 모드에서는 사용자가 넣은 수동값을 우선 사용
- `main_MP`와 실제 임무계획 GUI가 동일한 설정 파일을 공유

즉 테스트에서 바꾼 설정이 실제 모듈에도 같은 방식으로 적용된다.

## 7. 선행임무 재계획 시나리오

선행임무는 기존 협업기저임무 중간에
추가 개별임무를 끼워 넣는 방식으로 처리한다.

### 7.1 좌표지향 선행임무
예를 들어 현재 협업기저임무를 수행하던 중
특정 좌표를 잠깐 먼저 확인해야 하는 상황이다.

이 경우 구조는 아래처럼 된다.

1. 기존 임무에서 이미 수행한 구간은 잘라서 완료 처리
2. 선행임무용 개별임무를 새로 삽입
3. 원래 하던 임무의 남은 부분을 resume 개별임무로 다시 생성

즉
“기존 임무를 삭제”
하는 것이 아니라
“기존 임무 일부를 완료 처리하고, 사이에 새 임무를 끼워 넣고, 남은 임무를 재개”
하는 구조다.

### 7.2 표적지향 선행임무
좌표 대신 target ID가 들어오는 경우다.

이때는

- `targetInfo`에서 해당 target ID의 현재 좌표를 찾고
- 그 좌표로 추적/확인 임무를 생성한다

이 구조는 공격 재계획의 추적 UAV 생성 방식과 매우 유사하다.

### 7.3 다른 비행체는 어떻게 되는가
선행임무를 맡지 않은 UAV도
기존 임무를 처음부터 다시 수행하지 않도록 조정한다.

즉

- 이미 지난 waypoint는 잘라내고
- 필요한 경우 현재 진행 시점을 반영한 새 연결점만 남기고
- 남은 구간부터 다시 이어서 수행

하게 만든다.

## 8. 공격 재계획 시나리오

공격 재계획은 “표적 발견 → 추적 UAV 지정 → LAH 공격 계획 생성 → 나머지 임무 resume” 구조다.

## 8.1 어떤 표적이 공격 재계획 대상인가
표적이 들어오면 아무 표적이나 바로 공격하지 않는다.

아래 조건을 본다.

- `targetID > 0`
- 좌표가 유효
- `isDestroyed == false`
- `isUsed == 0`
- `isIgnored == 0`

즉,
- 이미 파괴된 표적
- 이미 재계획에 사용한 표적
- 좌표가 비정상인 표적

은 공격 재계획 대상이 아니다.

같은 타임스텝에 여러 표적이 들어오면
공격 슬롯 수 안에서 병렬 공격 재계획을 만들 수 있다.

## 8.2 표적을 본 UAV는 어떻게 바뀌는가
표적을 실제로 보고 있던 UAV는
기존 임무를 통째로 잃지 않는다.

구조는 다음과 같다.

1. 기존 임무의 수행 완료 구간을 완료 처리된 path로 유지
2. 새 추적 개별임무를 추가
3. 원래 하던 임무의 남은 구간을 resume 개별임무로 다시 생성

즉,
“완료 구간 / 추적 구간 / 이후 resume 구간”
의 세 조각으로 나뉜다.

## 8.3 다른 UAV들은 어떻게 되는가
추적하지 않는 UAV들도 기존 임무를 처음부터 다시 하지 않도록 조정된다.

현재 기준은 다음과 같다.

- 이미 지난 waypoint는 제거
- 현재 진행 중인 구간 이후만 남김
- 필요 시 중간 연결점 추가
- 촬영 sweep는 진행률을 반영해 일부 잘라낼 수 있음

즉 공격 재계획 때문에 다른 UAV가 처음부터 전체 구역을 다시 훑지 않게 한다.

## 8.4 LAH는 어떻게 계획되는가
공격 쪽 LAH는 다음 흐름을 가진다.

1. 적절한 유인기 선택
2. 표적 접근 경로 생성
3. 공격 waypoint 생성
4. 이탈 경로 생성

이때 LAH 경로는
- 불필요한 hovering / loiter / attack 블록 남발을 줄이고
- 실제 필요한 구간만 넣도록 정리되어 있다.

또한 같은 협업기저임무 안에서 개별임무가 이어져도
현재 정책상 개별임무 마지막 `nextWaypointID`는 `0`으로 통일한다.

## 9. 기존 임무를 유지하면서 재계획하는 방식

현재 재계획 로직의 중요한 원칙은 아래와 같다.

### 9.1 기존 임무를 지우지 않는다
재계획 시 예전 path를 통째로 삭제하지 않는다.

대신

- 이미 끝난 구간은 `isDone=true`로 남기고
- 새 path / 새 개별임무를 추가한다

이렇게 해야

- 시각화는 유지되고
- 실제 수행은 아직 안 끝난 임무부터 이어갈 수 있다.

### 9.2 현재 진행 시점을 반영한다
재계획 시에는 단순히 “다음 waypoint부터”가 아니라

- 현재 waypoint
- 실제 위치
- sweep 진행률

을 반영해 남은 임무를 만든다.

즉 resume 임무는
“원래 임무의 복사본”
이 아니라
“현재 시점 이후만 남긴 새 임무”
다.

## 10. 편대비행 시나리오

편대비행 임무는 leader/follower 구조로 만든다.

- leader도 편대비행 플래그를 가진다
- leader는 자기 자신을 leader ID로 가진다
- follower는 leader의 경로를 따라간다
- 현재는 leader waypoint 좌표뿐 아니라 waypoint ID도 그대로 가져오도록 정리되어 있다

즉 편대비행은
leader path를 기준으로
편대 간 상대 위치만 다르게 유지하는 구조다.

## 11. 고도, FOV, 속도는 어떻게 정해지는가

## 11.1 고도
- DEM 기반 지형고도 참조
- 기체별 고도 layer 적용
  - 예: 610 / 620 / 630
- mission ground 기준 위에 상대고도를 얹는 구조

즉 단순 고정 고도 한 개가 아니라
지형과 기체 순서를 반영한 고도를 쓴다.

## 11.2 FOV / SEP
- 일반 line/area는 DB 기반 사용 가능
- mode와 설정에 따라 수동값 사용 가능
- nadir는 고도 기준 DB 선택 규칙을 따름

## 11.3 속도
- 설정값과 DB 기반 속도 후보를 함께 사용
- 최종 계획은 scheduling / expected velocity 흐름과 연결된다

## 12. `main_MP`와 실제 모듈의 관계

현재는 테스트 GUI와 실제 임무계획 GUI가 따로 노는 구조를 줄이는 것이 중요한 원칙이다.

그래서 지금은

- `main_MP`
- `modules/mission_planning/mission_planning_gui.py`

가 같은 설정 파일을 공유하고,
같은 모드 이름을 쓰며,
가능한 한 같은 계획 흐름을 타도록 맞춰져 있다.

즉 테스트에서

- `Bearing_Par_Sweep`
- `Bearing_Ver_Sweep`
- `Nadir`
- `Custom`

을 바꾸면 실제 모듈도 같은 기준으로 계획해야 한다.

## 13. 실패 처리 시나리오

임무계획은 실패할 수 있다.
중요한 것은 “왜 실패했는지 운용자가 바로 알 수 있어야 한다”는 점이다.

현재는 아래 상황을 별도로 본다.

- `0201` 누락
- `0203` 누락
- 입력 형식 오류
- IMP 생성 실패
- FlightPath 생성 실패
- 일부 pathID 누락
- 공격/선행 파이프라인 내부 실패

이 경우

- 상세 traceback은 내부 로그에 남기고
- 운용자에게는 `0001` 공지로 핵심 원인을 한글 요약해서 보낸다

즉 “안 됨”이 아니라
“무엇 때문에 안 됐는지”를 공지하는 구조다.

## 14. 문서를 볼 때의 기준

이 문서를 읽을 때는 코드 파일 이름보다
아래 질문을 먼저 보면 된다.

1. 지금 상황이 초기계획인가, 일반 재계획인가, 선행임무인가, 공격 재계획인가
2. 대상 임무가 line인가, area인가, point인가, formation인가
3. 현재 모드가 `Bearing_Par`, `Bearing_Ver`, `Nadir`, `Custom` 중 무엇인가
4. 기존 임무를 유지해야 하는가, 중간에 끼워 넣어야 하는가, 남은 구간만 resume 해야 하는가

이 네 질문으로 보면 현재 임무계획의 대부분을 시나리오 수준에서 따라갈 수 있다.
